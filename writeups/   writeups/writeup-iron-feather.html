Its flight record and mission plan were locked behind a custom-encrypted container, and the encryption code lived inside the autopilot binary we were given. The task was to reverse the crypto, decrypt the mission datastore and the flight log, reconstruct what the drone was told to do, and work out what actually brought it down. Seventeen questions, all answered. Challenge Description From chapters 09–10 of the story: a mobile relay was traced to a car dumped in the Pavilion Road car park, and camera footage tied that relay to the drone. We had to recover the concealed flight record, reconstruct the mission, and establish the drone's fate. The custom code that wrote them is inside the px4 binary — which is the whole point, since the crypto is non-standard and has to be read out of the disassembly. Initial Analysis Both .encrypted files open with an eight-byte ASCII magic: dataman.encrypted starts PX4DMENC, flight.ulg.encrypted starts PX4ULENC. Same container, two magics. Searching the px4 binary for those magic constants leads to a parser at RVA 0x16fdb0 and a decrypt routine at 0x16fe10. The decrypt routine walks the OpenSSL EVP interface and fetches its cipher by name — AES-256-GCM, an authenticated mode. That detail matters later: the tag and the AAD have to be handled exactly or nothing verifies. The salt in both files is byte-for-byte identical, so one key would decrypt both. Tools used: a disassembler for the px4 binary, gdb to run one function inside the binary directly, and Python (pycryptodome + hashlib) to finish the key derivation and decrypt. Solution Approach Step 1 — Container format and header layout The obvious assumption is the usual layout — header, ciphertext, GCM tag stuck on the end. I tried that first and got a MAC failure and garbage, which at least confirmed the assumption was wrong rather than the key. Disassembling the decrypt routine at 0x16fe10 gives the real 60-byte structure, with the tag inside the header rather than at the tail: Offset Size Field 0 8 magic 8 4 version 12 4 plaintext length 16 16 salt 32 12 GCM IV 44 16 GCM tag 60 ... ciphertext The AAD is the first 44 bytes — everything up to the tag. Step 2 — The two-stage key derivation The decrypt routine calls a key-derivation function at RVA 0x170af0. It takes the 16-byte salt in rdi and writes 32 key bytes to rsi. Inside are two stages: Stage 1 — custom mixing loop. An XXTEA-flavoured 32-bit loop using the deltas 0x9e3779b9 and 0x61c88647, run 384 times over a block of hardcoded constants. It produces a fixed 104-byte intermediate "password." Critically, this stage never consumes the salt, so the intermediate is constant across both files. Stage 2 — standard KDF. The intermediate is fed straight into OpenSSL PBKDF2: 170d74: call 32e830 with passlen = 0x68 (104), saltlen = 0x10, iter = 0x2000 (8192), digest EVP_sha256, keylen = 0x20. So the custom KDF is at 0x170af0, the mixing loop runs 384 rounds, and the standard KDF is PBKDF2 (PBKDF2-HMAC-SHA256). Step 3 — Extracting the intermediate with gdb Rather than reimplement the mixing loop, I called it directly inside the binary. Getting a PIE ELF to run one function from starti fought back on three things (all fixed in the code section): the stack canary reading uninitialised TLS, an SSE alignment fault, and resolving the PIE load base. With those handled, the loop ran and produced the 104-byte intermediate. Trying to run stage 2 inside the binary returned 0 — OpenSSL's providers aren't initialised that early, so EVP_sha256 is dead. Simpler to finish in Python. Step 4 — Key recovery and decryption Feeding the intermediate into PBKDF2 in Python produced the AES-256 key, and both files decrypted with valid authentication tags: key = a40ba87b8a0e21d4ead98b917c4bf0f60cc65b25c614b93f107e5ed1e483d6ce Step 5 — Reading the mission datastore dataman is mostly zeroes. Scanning for IEEE-754 doubles in a plausible London range found 17 lat/lon pairs, all packed between 0x211c and 0x2680. Consecutive pairs sat 60 or 120 bytes apart, which gave away a 60-byte mission_item_s record (lat at +0, lon at +8, seven floats at +0x10, nav_cmd uint16 at +0x2c, frame at +0x30). Counting from 0x211c, 24 records run to 0x26b8, matching mission_result.seq_total = 24, all in one contiguous bank (bank 0). The release mechanism is the seq 10 / 11 / 12 triple: DO_SET_ACTUATOR to 1.0, hold two seconds, back to 0.0. The drop happens at seq 10. One trap: nav_cmd 187 is DO_SET_ACTUATOR, not DO_LAND_START (189) — mis-map it and you go hunting for a gripper command that doesn't exist. So: active bank 0, 24 mission items, payload release at item 10. The planned landing is seq 23 (NAV_LAND), stored as clean doubles 51.4997 / -0.1608. Step 6 — Positions, and the fussy sampling convention Every source of a "position" clusters within about a metre (home_position, EKF origin, the SIH_LOC_* params, raw GPS). The convention that actually scores is vehicle_global_position sampled at the event timestamp: Takeoff at t=287.084 ([commander] Takeoff detected) → 51.4996987, -0.1607999 Payload release at t=446.656 → 51.5035602, -0.1608417 The crash is the nasty one. The quadcopter's landed flag doesn't latch until t=577.312, fifty seconds after it was actually down. Trust the flag and you get the wrong point. The real moment is in the physics: vertical speed collapses from 9.76 m/s to 0.01 m/s between t=525.840 and t=525.856, giving 51.5016938, -0.1620929. Step 7 — The injected command and what it means The vehicle_command topic has 18 records. Seventeen account cleanly — ground-station traffic tagged 255/190 and mission commands tagged 1/1. One matches neither: t = 520.764 command = 420 param1 = 101 param2 = 1 source_system = 0 source_component = 0 target = 0/0 Command 420 is MAV_CMD_INJECT_FAILURE (missing from older pymavlink dialects, but this firmware knows it). The log's own text confirms it: inject failure unit: motor (101), type: off (1) → [control_allocator] Stopping motors (4095). param1 = 101 is the motor unit, param2 = 1 is "off." That's what put the drone down. For distance, the straight-line separation between release and injection is 224 m, but that's not what the question wants. Summing horizontal displacement between consecutive vehicle_local_position samples across t = 446.656 → 520.764 gives the ground track flown: 276.71 m, i.e. 277. Disarm: actuator_armed.armed goes 1 → 0 at t = 576.968, matching [commander] Disarmed by internal command. Nearest road: reverse geocoding wasn't reachable, so I triangulated 51.5016938, -0.1620929 against fixed references (Knightsbridge tube station 87 m due east on the same latitude, Edinburgh Gate 66 m north). The point sits at the latitude the A4 runs there — Knightsbridge. Code / Exploit Calling the mixing loop inside the PIE binary from gdb, then finishing in Python. The three gdb fixes are the interesting part: # Break at entry so nothing has run yet starti # 1) Stack canary: the function reads %fs:0x28 but TLS isn't set up this early. # Point fs_base at a writable page. set $fs_base = # 2) SSE alignment: movaps 0x20(%rsp) needs 16-byte alignment. # Make the stack look like it does right after a call. set $rsp = ($rsp & ~0xF) - 8 # 3) PIE base: read it from the mappings and add RVAs. info proc mappings # load base e.g. 0x555555554000 # call the KDF's mixing stage at base + 0x170af0, then dump the 104-byte intermediate import hashlib, binascii from Crypto.Cipher import AES # 104-byte intermediate recovered from gdb PASS = binascii.unhexlify("696a8765...ab16f") d = open(fn, 'rb').read() salt = d[16:32]; iv = d[32:44]; tag = d[44:60] ct = d[60:]; aad = d[0:44] # AAD = first 44 bytes, tag lives inside the header key = hashlib.pbkdf2_hmac('sha256', PASS, salt, 8192, 32) c = AES.new(key, AES.MODE_GCM, nonce=iv); c.update(aad) pt = c.decrypt_and_verify(ct, tag) # tag verifies -> key is correct # key = a40ba87b8a0e21d4ead98b917c4bf0f60cc65b25c614b93f107e5ed1e483d6ce Technical Details Encryption: AES-256-GCM, authenticated, with the 16-byte tag stored at header offset 44 (not appended at EOF) and the first 44 bytes used as AAD. Key derivation: two stages — a custom 384-round XXTEA-flavoured 32-bit mixer producing a fixed 104-byte intermediate, then standard PBKDF2-HMAC-SHA256 (8192 iterations) to the 32-byte AES key. The mixer ignores the salt, so the intermediate is shared across both files. Mission format: PX4's dataman datastore, 60-byte mission_item_s records, 24 of them in bank 0. Flight log: PX4 ULog. Positions read from vehicle_global_position at event timestamps; the landed flag lags real ground contact by ~51 seconds, so ground contact has to be read from the vertical-speed collapse instead. The takedown: MAV_CMD_INJECT_FAILURE (MAVLink command 420), motor unit, type off. Key Insights To find custom crypto in a large binary, search for the file magic and follow cross-references to the parser and decrypt routine. Cheaper than reading everything. Read the header layout out of the disassembly instead of assuming tag-at-EOF. Here the tag sat mid-header. Calling a function inside a PIE binary from gdb needs three fixes up front: $fs_base for the canary, $rsp alignment for SSE loads, and the load base from info proc mappings. Then know when to stop emulating — OpenSSL's providers weren't initialised early enough for stage 2, so Python finished it. You can derive an undocumented record size from the stride between recognisable field values (IEEE-754 doubles in a known coordinate range). Check MAVLink command IDs against the spec, not memory: 187 is DO_SET_ACTUATOR, 189 is DO_LAND_START, and 420 is missing from older pymavlink entirely. Trust telemetry physics over firmware state flags, and when a question says "distance," decide whether it means straight-line or distance flown — they were 50+ metres apart here. What was new to me This was the challenge I learned the most from. Calling a function directly inside a PIE binary from gdb — fixing $fs_base so the stack canary wouldn't fault, realigning $rsp for the SSE loads, and resolving the load base out of info proc mappings — was new to me, and it turned "reimplement this whole KDF by hand" into "just run the code that's already here." Reading a custom crypto header layout straight out of the disassembly instead of assuming the usual tag-at-EOF was another habit this one drilled into me. And deriving an undocumented record size from the stride between recognisable field values (the IEEE-754 doubles) is a trick I hadn't tried before but will absolutely reuse.
